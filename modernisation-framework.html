1. When to use this framework

Pick a north star before launching agents. Mixing strategies randomly is how migrations stall.

01

Modular monolith

Often the right first step

Clear packages, enforced boundaries, same deployable. Use when the domain is still one product and ops cost of many services is not justified.

02

Service extraction

Strangler at the edge

Peel one bounded context with API + data ownership. Requires contract tests, flags, and a data cutover plan before code moves.

03

Platform upgrade

Same shape, newer runtime

Java LTS, Spring Boot major, Node LTS, framework bumps. Characterisation tests and dual-run matter more than new architecture diagrams.

04

Language / stack migration

Highest risk

COBOL→Java, Perl→Go, etc. Comprehension and characterisation first. Hard profiles (HIL, mainframe) often cannot run agent-invoked tests — set that expectation before the pilot.

Thesis: Agents raise the volume of diffs. Tests and CI become more important, not less. Velocity without gates is how regressions scale.

2. SDLC: Plan and Design before conversion

The conversion agents only run after a human-approved plan. Cursor Plan Mode (Shift+Tab / /plan) is the product surface — agents do not invent org architecture in silence.

3. Agent roster and orchestration

Orchestration is required. It never writes production code. It holds run state, spawns the next agent with the previous artefact, and refuses to skip gates.

Orch→ Discovery→ Plan/Design→ Gate→ Test gen→ Test exec→ Conversion→ Dual-run→ Bugbot→ Security→ Validation→ Sign-off
0
Orchestration agent

Owns RUNBOOK.md: phase, owners, path allowlists, stop conditions, merge-train branch. Spawns specialists; serialises conflict/CI fix (one agent). Never edits production code.

1
Discovery agent

Documents process tree, binaries, manifests/lockfiles, verify command, connectivity, hottest packages, non-overlapping slice proposals → LEGACY_MAP.md. Docs-only PR.

2
Plan & Design agent

Produces PLAN.md + ADR (modular monolith vs extract vs platform upgrade; data strategy; flags; rollback). Human must accept before tests or conversion.

3
Test generation agent

Characterisation, unit, integration, thin UAT/E2E for revenue paths. Tests-only PRs. Do not “fix” legacy bugs in this phase.

4
Test execution agent

Runs the same suite against legacy and modernised; stores reports; fails the runbook on drift. Inner loop = format → lint → types → unit. CI is source of truth.

5
Conversion agent

Executes migration with skills and rules; hard path allowlist; spawns parallel slice sub-agents (typically 3–6). One mergeable PR per slice. Merge shepherd is serial when files collide.

6
Bugbot

Every conversion PR via Automations; /review-bugbot before push. Beside CI, not instead of it. Autofix → Cloud Agent on a new branch (recommended).

7
Security Agents

Security Reviewer on each PR; Vulnerability Scanner on a cron against the integration branch. Wire findings via MCP. Complements — does not replace — dependency CVE scanning.

8
Validation agent

Evidence pack for human sign-off: dual-run reports, Bugbot/security summaries, ADR + change notes, rollback, observability delta.

5. Verification ladder and PR definition of done

Cheap checks run constantly; expensive checks run at gates. Teams that invert this stop running tests. The “fast four” — format, lint, type check, unit tests — are the agent write loop.

Enforcement layers

Layer 1

Editor — on save

.vscode/settings.json: format and auto-fixable lint for whoever wrote the file.

Layer 2

Cursor rule — after edits

Agent runs the fast four after changing code. Glob-scoped per language; always-on verification rule stays short.

Layer 3

Hook — pre-commit

Backstop for anyone who bypassed the first two. Keep it fast or people use --no-verify.

Also write AGENTS.md at the repo root so multi-tool agent ecosystems share the same verification instructions. Pair with .cursor/BUGBOT.md for review rules.

Definition of done for an agent PR: format + lint/types + unit (touched packages) green locally; CI green on the PR; characterisation or new tests for any behaviour you intended to keep; no drive-by refactors outside the slice; Bugbot and Security Reviewer have run (or are required checks).

6. Bugbot and Security Agents in the merge path

Human review shifts up: boundaries, data migration, rollout risk — not “does it compile?” AI review sits beside required status checks.

Bugbot

PR review for bugs and quality

Automatic on PR updates, or cursor review / bugbot run. Locally: /review-bugbot before push (syncs via patch ID with SCM review).

Optional: require Cursor Bugbot check; enable fail-on-unresolved if available. Autofix → new branch, max attempts capped.

Security Reviewer

PR security gate

Automations on PR events. Locally: /review-security. Catches injection, authz gaps, unsafe patterns introduced by conversion.

Vulnerability Scanner

Cron on integration branch

Finds long-standing issues PR bots miss. Schedule against the merge-train branch during active modernisation.

Rules

.cursor/BUGBOT.md

Migration-specific: no drive-by refactors; tests required for backend; licence scan on lockfile edits; flag eval/exec and secret patterns.

Trust CI, not the model’s claim that tests passed. Required status checks protect main. Bugbot findings default to neutral unless you configure fail-on-unresolved — know which behaviour your org has.

7. MCP and Automations map

Suggest, do not require. Least privilege; secrets in the Cloud Agent dashboard — never git. Treat mcp.json like Terraform.

Automations as event-driven orchestration

  • PR opened / pushed → Bugbot + Security Reviewer
  • CI failed → triage / fix agent (serial; path-aware)
  • Linear status → Ready → spawn next approved slice
  • Nightly cron → Vulnerability Scanner + evidence refresh
  • PagerDuty / Sentry → investigate during cutover window
Cloud Agent environment is a prerequisite. An unset env is like not giving engineers a computer. Confirm one “hello” agent can open a trivial PR that stays green before fanning out slices.

8. Slice / strangler playbook

0
Prep the Cloud Agent environment

Connect SCM. Configure env so deps install and the project test command runs. Secrets via dashboard. Smoke-test a docs-only PR.

1
Map the system

1–2 scout agents → architecture brief. Output = markdown + diagrams. No behaviour change.

2
Raise the safety net

Parallel characterisation / unit tests on seams you’ll cut. Many small PRs. No production refactors except minimal testability (called out).

3
Draw target boundaries

Human decides north star. One-page ADR. Agents do not invent architecture in silence.

4
Fan out slice agents

One Cloud Agent per bounded context, own branch, hard path allowlist. Independently mergeable PRs; feature-flagged if risky.

5
Integrate on a train

Merge green slices frequently into an integration branch (or main behind flags). Re-run full CI. One merge shepherd — don’t let five agents fight the same files.

6
Harden, observe, then delete

Integration/E2E for new boundaries; flag cutovers; watch metrics. Bugbot + Security on PRs. Only then delete dead legacy paths.

9. Migration best practices (beyond the companion notes)

Expand / contract

Parallel change for APIs and schemas. Never break callers in the same PR as a rename. Add → migrate consumers → remove.

Branch by abstraction

Sibling of strangler when you cannot route at the edge. Introduce a seam, swap implementations behind it, delete the old path last.

Data migration sequence

Expand schema → dual-write → backfill → dual-read → drop. Idempotent, replayable jobs. Version every migration.

Shadow / dark launch

Send production traffic to the new path, compare outputs, do not cut over on green unit tests alone.

Feature flags + kill switch

Prove in production (or flagged + smoke) before deleting legacy. Instant rollback without a revert train.

Contract tests at seams

OpenAPI snapshots, Pact, or consumer-driven contracts so slice agents cannot silently break neighbours.

Observability before code

Golden signals, error budget, log/trace IDs. Validation compares after vs before — not vibes.

Performance baseline

Same hardware shape. The top rung of the ladder is usually where migrations fail late.

Compatibility window

Consumer versioning; freeze unrelated dependency churn during a slice.

SBOM + lockfile CI

npm ci not npm install. The lockfile is the guarantee. Installing is not vetting.

Secrets and env parity

Cloud Agent image ≈ CI image. Dashboard secrets. No .env in git.

Split behaviour from structure

Do not mix product behaviour change with structural refactor. Impossible to review — split PRs.

Coverage is not quality

Easy to game. Pair with change-failure rate and time to restore.

Hard profiles

C/C++ HIL, COBOL: comprehension and characterisation first. Agents often cannot invoke the rig at all.

Merge train + shepherd

Daily rebase cadence; one serial agent when paths overlap. Conflict hell is an ownership failure.

Rollback in the evidence pack

A runbook, not a slide. Flags, data reverse path, and who pages whom.

10. Human gates and evidence pack

Agents must stop for

  • Plan / ADR not yet accepted by a human owner
  • First production cutover (or first traffic to a new path)
  • Deleting a legacy path or shutting off dual-write
  • Intentional behaviour change mixed into a structural PR — split first
  • Dual-run drift unresolved (legacy vs modern disagree)
  • Unresolved high-severity Security or Bugbot findings (per org policy)

Evidence pack checklist

  • LEGACY_MAP.md + approved PLAN.md / ADR
  • Characterisation + unit/integration inventory; tests-only PRs merged
  • Dual-run reports (legacy SHA vs modern SHA) with identical command
  • CI green on merge-train; required checks listed
  • Bugbot summary (findings + resolutions)
  • Security Reviewer + Vulnerability Scanner summaries
  • Observability baseline vs after (golden signals)
  • Feature-flag state and kill-switch owner
  • Rollback runbook (data + traffic + code)
  • Human go / no-go signature and date

11. Prompt skeletons

Hand off the outcome and constraints — not a line-by-line prescription. Always include how to prove done.

Orchestrator

You are the orchestration agent for a strangler modernisation.
You never edit production code. You only update RUNBOOK.md and spawn specialists.

State machine: discover → plan_design → (human_gate) → test_gen → test_exec_baseline
→ conversion → test_exec_dual → bugbot → security → validation → human_signoff.

Rules:
- Refuse to advance if a required artefact is missing or a human gate is open.
- Spawn slice agents with non-overlapping path allowlists only.
- Conflict/CI fix: one agent at a time.
- After each specialist finishes, verify their artefact exists and update RUNBOOK.md phase.
- Report blockers; do not invent verify commands.

Discovery (scout)

You are mapping [repo] for a strangler modernisation.
Read-only except for adding docs/architecture/LEGACY_MAP.md.

Deliver:
1) Module/package map and runtime entrypoints / process tree
2) Binaries, manifests, lockfiles, and the verify command(s)
3) Data stores and external integrations / connectivity
4) Existing test layout and CI workflow paths
5) Top 5 risky hotspots for extraction (with file paths)
6) Suggested vertical slices for parallel agents (non-overlapping paths)

Do not change production code. Open a PR with only the doc.

Plan & Design

Using LEGACY_MAP.md, draft PLAN.md and docs/adr/0001-north-star.md.

Choose ONE north star: modular monolith | service extraction | platform upgrade.
Include: slice sequence, path allowlists, data/cutover strategy, feature flags,
rollback, acceptance criteria, and stop conditions.

Use Plan Mode style: options with trade-offs, then a recommended path.
Do not change production code. Mark status: awaiting_human_approval.

Characterisation / test generation

Add characterisation tests for [component] capturing current behaviour
(including odd edge cases). Cover unit + relevant integration seams.
Do not “fix” production bugs in this PR.
Path allowlist: [tests/... and minimal harness only].
Run [verify command] until green. PR = tests (+ minimal harness) only.
List behaviours locked in the PR description.

Conversion (slice)

Goal: [e.g. extract Owners domain behind a clear package API]
Branch: refactor/owners-boundary
Path allowlist: [src/.../owner/**, tests/.../owner/**] ONLY.

Constraints:
- No behaviour change visible to users unless listed in "Intentional changes"
- After every edit cycle run: [PROJECT VERIFY COMMAND]
- Also run formatter/linter/typecheck as used in CI
- Add/adjust unit tests for any moved logic
- Keep the PR small; stop when CI is green and the boundary exists
- Do not touch files outside the allowlist

Definition of done:
- Verify command green locally
- CI green on the PR
- Short PR description: before/after structure, test evidence, risks
- Ready for /review-bugbot and /review-security

Dual-run test execution

Run the same test suite against legacy ref [LEGACY_SHA] and modern ref [MODERN_SHA]
using identical command: [verify command].
Store reports under evidence/reports/{legacy,modern}/.
Compare results; fail RUNBOOK if any intentional-keep behaviour drifts.
Do not change production code. Update evidence/reports/SUMMARY.md with SHAs and outcomes.

Validation

Produce evidence/EVIDENCE_PACK.md for human sign-off.
Assemble: LEGACY_MAP, PLAN/ADR, test inventory, dual-run SUMMARY,
CI check list, Bugbot findings, Security Reviewer + Vulnerability Scanner summaries,
observability delta, flag/kill-switch owner, rollback runbook.
Recommend go or no-go with residual risks. No production code changes.

12. Anti-patterns

  • Big-bang rewrite agent — one agent, whole repo, multi-thousand-line PR.
  • Overlapping path ownership — two agents editing the same package → merge hell.
  • Skipping Plan / ADR — conversion before a human north star.
  • Green locally, skip CI — Cloud Agent env drifted from CI image.
  • Refactor while “also” changing product behaviour — impossible to review; split PRs.
  • Deleting legacy before the strangler path is proven (or at least flagged + smoke-tested).
  • Trusting the model’s claim that tests passed — require CI status checks.
  • Using Bugbot or Security Agents instead of required checks — they sit beside CI.
  • Autofix committing straight to the slice branch in a loop — prefer new-branch autofix.
  • No dual-run — modern suite green while silently changing legacy behaviour.
  • Coverage theatre — charting coverage up while change-failure rate is ignored.

13. Onboarding diagnostic

Ask these in the first technical session. The answers predict time-to-value better than any architecture diagram.

  1. What does a developer run locally before they push?

    If the answer is “nothing, CI catches it”, the agent has no way to check its own work — every mistake costs a full pipeline cycle.

  2. Is there one command that runs the checks?

    make check, npm run verify, a documented task. If verification is six undocumented CI steps, consolidate that first — a fast, high-value win.

  3. How long does the test suite take?

    Under two minutes is a healthy loop. Forty minutes means developers (and agents) batch changes. Split out a fast subset.

  4. How many languages are in the main repository?

    Polyglot monorepos mean several package managers, lockfiles, and test commands. Cross-language resolution is a common failure mode.

  5. Can build machines reach the public registry?

    Usually not. Find the internal proxy and approval path — it governs how quickly anything new can be introduced, including agent tooling.
